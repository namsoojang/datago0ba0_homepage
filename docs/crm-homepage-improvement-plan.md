# 데이터공방 CRM 홈페이지 단계별 개선 계획

작성일: 2026-07-18  
적용 스킬: `$improve-crm-homepage`

## 1. 목표

홈페이지를 단순 소개 페이지가 아니라 다음 고객 여정이 자연스럽게 이어지는 B2B CRM 접점으로 개선한다.

```text
검색·소개 유입
→ 데이터공방의 대상 고객과 성과 이해
→ 실제 사례와 전문성 확인
→ 교육·도구·가이드 중 목적에 맞는 경로 선택
→ 낮은 부담의 자료 탐색
→ 교육·협업 상담 의도 형성
→ CRM 접수와 후속 응답
```

## 2. 진행 원칙

- 한 번에 하나의 퍼널 문제만 개선한다.
- 각 단계는 별도 커밋으로 만들고 검증 후 푸시한다.
- 실제 사례와 확인 가능한 근거만 사용한다.
- 기존 미커밋 변경을 임의로 포함하거나 덮어쓰지 않는다.
- 데스크톱과 모바일을 함께 검증한다.
- 구현 전에 성공 판단 이벤트나 지표를 정한다.
- 구조 변경이나 신규 의존성은 별도 승인을 받는다.

## 단계 0. Git 기준선과 배포 구조 정리

### 목적

현재 Worktree의 미커밋 변경을 보존하면서 `review/codex`, `main`, GitHub와 서버 배포 기준을 명확히 한다.

### 작업

1. 두 Worktree의 브랜치, 변경 파일, 원격 차이를 확인한다.
2. 사용자 변경과 이전 에이전트 변경을 분류한다.
3. 서버가 실제로 배포하는 브랜치를 확인한다.
4. CRM 개선용 깨끗한 작업 기준점을 만든다.
5. `.agents/skills/improve-crm-homepage`를 별도 커밋한다.

### 완료 기준

- 기존 변경이 유실되지 않는다.
- 다음 단계에서 관련 파일만 커밋할 수 있다.
- 배포 브랜치와 병합 순서가 문서화된다.

### 실행 프롬프트

```text
$improve-crm-homepage를 사용해 데이터공방 홈페이지 CRM 개선의 0단계를 진행해줘.

이번 단계에서는 홈페이지 코드를 수정하지 말고 Git 기준선만 정리해줘.
현재 0_홈페이지와 0_홈페이지_codex Worktree의 브랜치, 미커밋 변경, 원격 브랜치 차이, 서버 배포 브랜치를 확인해줘.
기존 사용자 변경은 절대 덮어쓰거나 다른 커밋에 섞지 말아줘.

결과로 다음을 남겨줘.
1. 현재 Git 상태 요약
2. 변경 파일의 소유·목적 분류
3. 안전한 작업 브랜치와 병합 순서
4. 서버 배포까지의 절차
5. .agents/skills/improve-crm-homepage만 별도 커밋·푸시 가능한지 판단

읽기 전용 점검을 먼저 수행하고, 커밋이나 푸시 전에는 포함 파일을 정확히 보여줘.
```

## 단계 1. 전역 메뉴 통일

### 목적

모든 페이지에서 동일한 사이트 구조를 제공하고 `실무가이드`와 `교육·협업 문의`의 발견성을 높인다.

### 권장 전역 메뉴

```text
로고
교육·서비스
성과·사례
업무도구
실무가이드
블로그
[교육·협업 문의]
```

가이드와 업무도구의 세부 항목은 전역 메뉴를 대체하지 않고 보조 메뉴로 둔다.

### 대상

- `index.html`
- `blog.html`, `blog-detail.html`
- `rpa.html`
- 각 업무도구 HTML
- `privacy.html`
- `guide/index.html`
- 두 Antigravity 가이드

### 완료 기준

- 메뉴 이름과 순서가 동일하다.
- 루트와 하위 폴더의 상대경로가 모두 정상이다.
- 현재 페이지에 활성 상태 또는 `aria-current`가 있다.
- 900px 이하에서 햄버거 메뉴와 CTA가 정상 동작한다.
- 로컬 링크 누락과 중복 ID가 없다.

### 측정

- `click_global_nav`
- 속성: `nav_item`, `source_page`
- Guide 허브 진입률
- 문의 CTA 클릭률

### 실행 프롬프트

```text
$improve-crm-homepage를 사용해 1단계인 전역 메뉴 통일만 진행해줘.

먼저 모든 HTML 페이지의 현재 메뉴를 표로 비교하고, menu-standard.md의 권장 구조를 기준으로 최종 메뉴 명세를 제시해줘.
전역 메뉴는 교육·서비스 → 성과·사례 → 업무도구 → 실무가이드 → 블로그 → 교육·협업 문의 순서로 통일해줘.
홈 이동은 로고가 담당하게 하고, 가이드·업무도구의 세부 메뉴는 보조 탐색으로 분리해줘.

필수 조건:
- 기존 본문과 기능은 수정하지 않기
- 루트·하위 폴더 상대경로 정확히 처리
- aria-current와 모바일 aria-expanded 처리
- 데스크톱·모바일 시각 검증
- 모든 로컬 링크와 인라인 JavaScript 검사
- 이번 메뉴 관련 파일만 커밋

구현 전 영향 파일과 제외 범위를 먼저 알려주고, 완료 후 변경 전후 메뉴 표와 다음 우선순위를 보고해줘.
```

## 단계 2. Hero 메시지와 CTA 정리

### 목적

첫 화면에서 `누구를 위해 무엇을 해결하는지`를 5초 안에 이해시키고 행동을 두 가지로 압축한다.

### 결정할 항목

- 핵심 대상: 기업 교육 담당자, 현업 실무팀, 자동화 협업 고객 중 우선순위
- 핵심 결과: 현업 적용, 반복 업무 자동화, 검증 가능한 AI 활용 중 하나
- 주요 CTA: `기업 교육·협업 문의`
- 보조 CTA: `실무 가이드 보기` 또는 `적용 사례 보기`

### 완료 기준

- Hero 제목이 대상과 성과를 함께 설명한다.
- 한 화면에 주요 CTA와 보조 CTA만 경쟁한다.
- 과장되거나 검증되지 않은 수치가 없다.
- 모바일 첫 화면에서도 핵심 메시지와 CTA가 보인다.

### 실행 프롬프트

```text
$improve-crm-homepage를 사용해 2단계 Hero 메시지와 CTA만 개선해줘.

현재 Hero, About, Curriculum, Contact의 문구를 읽고 중복과 메시지 충돌을 진단해줘.
데이터공방의 실제 강점과 확인 가능한 사례를 기준으로 핵심 대상 고객 1순위와 핵심 결과 1개를 제안해줘.

구현 전 다음 3가지 카피 안을 비교해줘.
- 보수적 안
- 성과 중심 안
- 교육 담당자 중심 안

선택한 안으로 Hero 제목, 설명, 주요 CTA, 보조 CTA만 수정해줘.
검증되지 않은 성과 수치나 고객 로고는 추가하지 말아줘.
데스크톱·모바일 시각 검증과 CTA 링크 검증 후 관련 파일만 커밋·푸시해줘.
```

## 단계 3. 신뢰 근거와 사례 구조화

### 목적

방문자가 문의 전에 강사와 데이터공방의 실제 수행 역량을 확인할 수 있게 한다.

### 사례 카드 구조

```text
대상 조직·수강자
→ 해결할 문제
→ 교육·자동화 개입
→ 확인 가능한 결과 또는 산출물
→ 관련 사례·문의 CTA
```

### 사용할 수 있는 근거

- 실제 출강 기관과 허용된 로고
- 교육 현장 사진
- 강의 주제와 대상 직무
- 공개 가능한 후기
- 실제 도구와 결과물
- 재출강·후속 문의처럼 확인 가능한 사실

### 완료 기준

- 로고 나열만 하지 않고 사례 맥락이 있다.
- 각 주장에 확인 가능한 출처가 있다.
- 사례에서 관련 서비스 또는 문의로 이동할 수 있다.

### 실행 프롬프트

```text
$improve-crm-homepage를 사용해 3단계 신뢰 근거와 사례 구조화만 진행해줘.

기존 References, 블로그 게시물, 이미지 자산과 프로젝트 문서에서 공개 가능한 실제 사례를 찾아 목록화해줘.
각 사례를 대상 → 문제 → 개입 → 결과·산출물 → 다음 행동 구조로 정리해줘.

확인되지 않은 수치, 기관명, 후기, 로고 사용 권한은 추정하지 말고 사용자 확인 필요 항목으로 분리해줘.
우선 대표 사례 3개만 홈페이지에 적용하고 나머지는 후속 후보로 남겨줘.
완료 후 사례별 근거 파일, 수정 파일, CTA 경로와 검증 결과를 보고하고 관련 파일만 커밋·푸시해줘.
```

## 단계 4. 방문 목적별 서비스 경로

### 목적

방문자가 기술 이름이 아니라 자신의 상황을 기준으로 다음 페이지를 고르게 한다.

### 권장 경로

| 방문 상황 | 연결 경로 |
|---|---|
| 임직원 AI 활용 교육이 필요함 | 교육·커리큘럼 |
| 반복 업무를 자동화하고 싶음 | 업무도구·기술 협업 |
| 혼자 먼저 학습하고 싶음 | 실무가이드 |
| 실제 수행 경험을 확인하고 싶음 | 성과·사례 |

### 완료 기준

- 서비스 카드의 제목이 고객 상황을 사용한다.
- 카드마다 얻는 결과와 다음 화면이 분명하다.
- 유사한 서비스 카드와 CTA가 중복되지 않는다.

### 실행 프롬프트

```text
$improve-crm-homepage를 사용해 4단계 방문 목적별 서비스 경로만 개선해줘.

현재 Curriculum, RPA, Guide, Blog, Contact의 관계를 분석하고 방문 목적 기준의 정보구조를 제안해줘.
교육이 필요함, 반복 업무 자동화가 필요함, 먼저 학습하고 싶음, 실제 사례를 보고 싶음의 네 경로를 우선 사용해줘.

각 경로에 다음을 작성해줘.
- 고객 상황
- 기대 결과
- 연결 페이지
- CTA 문구
- 측정 이벤트

기존 기능은 삭제하지 말고 중복 카드와 모호한 CTA만 정리해줘.
링크와 모바일 카드 배치를 검증하고 관련 파일만 커밋·푸시해줘.
```

## 단계 5. 가이드·PDF 전환 흐름

### 목적

정보 탐색 방문자가 다음 가이드, 사례, 상담으로 자연스럽게 이동하게 한다.

### 점검 항목

- 홈페이지와 전역 메뉴에서 Guide 허브 발견 가능
- STEP 01 → STEP 02 → 팀 적용 상담의 연결
- PDF 직접 다운로드와 상담 폼 분리
- 다운로드와 다음 단계 CTA 측정
- PDF와 웹 본문의 공개 내용 일치

### 실행 프롬프트

```text
$improve-crm-homepage를 사용해 5단계 가이드·PDF 전환 흐름을 점검하고 개선해줘.

guide/index.html, 두 Antigravity 웹 가이드, 두 PDF, 홈페이지 Guide 소개 영역을 하나의 고객 여정으로 검토해줘.
STEP 01 시작 → STEP 02 Rules & Skills → STEP 03 교육·도입 상담 구조가 모든 진입점에서 보이는지 확인해줘.

PDF는 바로 다운로드 가능하게 유지하고, 상담 폼은 별도 고의도 CTA로 구분해줘.
웹과 PDF에 내부 제작 문구가 노출되지 않는지 확인해줘.
download_guide_pdf, select_guide_step, click_team_consultation 이벤트를 점검해줘.
누락된 부분만 최소 수정하고 검증 후 관련 파일만 커밋·푸시해줘.
```

## 단계 6. 문의 폼과 CRM 데이터 품질

### 목적

폼 이탈을 줄이면서 후속 상담에 필요한 맥락을 확보한다.

### 권장 필드

- 필수: 이메일, 문의 내용 또는 관심 분야, 개인정보 동의
- 선택: 이름, 회사·기관, 직책, 예상 일정
- 자동 수집: 유입 페이지, 선택 가이드, 문의 유형, 제출 시각

### 완료 기준

- 수집 목적과 후속 연락 기대치가 보인다.
- 입력 오류와 성공·실패 상태가 명확하다.
- CRM에 문의 유형과 유입 맥락이 저장된다.
- 개인정보처리방침과 실제 수집 항목이 일치한다.

### 실행 프롬프트

```text
$improve-crm-homepage를 사용해 6단계 문의 폼과 CRM 데이터 품질만 개선해줘.

현재 홈페이지와 가이드의 모든 문의·다운로드 폼, GAS 전송 payload, 개인정보처리방침을 함께 점검해줘.
필수 필드는 최소화하되 관심 분야, 유입 페이지, 상담 유형이 CRM에 저장되게 설계해줘.

반드시 확인할 것:
- 개인정보 동의 문구와 처리방침 일치
- 이메일·필수값 검증
- 중복 제출 방지
- 성공·실패·네트워크 오류 메시지
- 제출 버튼 복구
- GA4 이벤트 중복 전송 여부

외부 CRM 스키마나 Apps Script 변경이 필요하면 현재 코드에서 확인 가능한 범위와 사용자 확인이 필요한 범위를 분리해줘.
테스트 가능한 프런트엔드 변경부터 구현하고 관련 파일만 커밋·푸시해줘.
```

## 단계 7. FAQ와 반대 질문 해소

### 목적

교육·협업 문의 전에 발생하는 비용, 일정, 적합성, 보안과 준비 관련 불안을 해소한다.

### FAQ 후보

- 어떤 직무와 수준에 적합한가?
- 교육 시간과 인원은 어떻게 정하는가?
- 우리 회사 데이터로 실습할 수 있는가?
- 보안과 개인정보는 어떻게 처리하는가?
- 커리큘럼은 조정 가능한가?
- 온라인·오프라인 모두 가능한가?
- 자동화 협업은 어떤 방식으로 진행되는가?
- 비용과 일정은 언제 확정되는가?
- 적합하지 않은 의뢰도 있는가?

### 실행 프롬프트

```text
$improve-crm-homepage를 사용해 7단계 FAQ만 설계하고 구현해줘.

기존 문의 폼, 프로젝트 문서, 교육 사례와 홈페이지 문구에서 실제 방문자가 망설일 질문을 찾아줘.
가격을 임의로 만들거나 보안·성과를 보장하지 말고, 확인 가능한 운영 방식만 답변해줘.

FAQ 8개 이내로 우선 구성하고 질문을 적합성, 진행 방식, 보안, 비용·일정 순으로 배치해줘.
구조화 데이터 FAQPage 적용 가능성도 검토하되 Google 정책과 실제 화면 내용이 일치할 때만 추가해줘.
접근 가능한 아코디언과 모바일 동작을 검증하고 관련 파일만 커밋·푸시해줘.
```

## 단계 8. GA4 퍼널 측정

### 목적

어떤 페이지와 콘텐츠가 상담으로 이어지는지 판단한다.

### 핵심 이벤트

| 이벤트 | 속성 |
|---|---|
| `click_global_nav` | `nav_item`, `source_page` |
| `view_guide_hub` | `source_page` |
| `select_guide_step` | `step`, `guide_name` |
| `download_guide_pdf` | `guide_name`, `source_page` |
| `click_team_consultation` | `source_guide`, `source_page` |
| `submit_contact_form` | `inquiry_type`, `source_page` |

### 완료 기준

- 이벤트 이름과 속성이 페이지마다 동일하다.
- 클릭과 제출이 중복 집계되지 않는다.
- 개인정보를 GA4 속성으로 보내지 않는다.
- 이벤트 점검 방법이 문서화된다.

### 실행 프롬프트

```text
$improve-crm-homepage를 사용해 8단계 GA4 퍼널 측정만 진행해줘.

현재 gtag와 GTM 설치 위치, 기존 이벤트 이름, 폼 이벤트, PDF 다운로드 이벤트를 전수 조사해줘.
중복 태깅과 페이지별 불일치를 먼저 보고한 뒤 공통 이벤트 명세를 확정해줘.

개인정보, 이메일, 이름, 회사명, 자유 입력 문의 내용은 GA4로 전송하지 말아줘.
이벤트는 click_global_nav, view_guide_hub, select_guide_step, download_guide_pdf, click_team_consultation, submit_contact_form을 기준으로 통일해줘.
각 이벤트의 테스트 절차와 GA4에서 볼 퍼널 정의를 문서로 남기고 관련 파일만 커밋·푸시해줘.
```

## 단계 9. 접근성·성능·최종 일관성

### 목적

CRM 개선으로 추가된 UI가 모든 기기에서 안정적으로 동작하게 한다.

### 점검

- 키보드 탐색과 포커스
- 색상 대비와 폰트 크기
- 메뉴·FAQ의 ARIA 상태
- 이미지 대체 텍스트와 크기
- 모바일 오버플로와 터치 영역
- 중복 추적 스크립트
- 깨진 링크와 404
- Core Web Vitals에 영향을 주는 외부 스크립트

### 실행 프롬프트

```text
$improve-crm-homepage를 사용해 9단계 최종 품질 점검을 진행해줘.

이번 단계에서는 새로운 마케팅 섹션을 추가하지 말고 메뉴, CTA, 폼, 가이드 허브, FAQ와 GA4 변경의 접근성·성능·일관성만 검토해줘.
데스크톱과 모바일을 시각 확인하고 키보드 탐색, 포커스, ARIA, 색상 대비, 터치 영역, 오버플로, 이미지 alt, 깨진 링크, JavaScript 오류를 검사해줘.

문제를 심각도별로 분류하고 안전한 수정만 구현해줘.
구조 변경이나 신규 의존성이 필요하면 구현하지 말고 별도 제안으로 남겨줘.
최종 회귀 검증 후 관련 파일만 커밋·푸시하고 전체 CRM 개선 완료 보고서를 작성해줘.
```
